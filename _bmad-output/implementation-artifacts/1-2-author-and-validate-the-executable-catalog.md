# Story 1.2: Author and Validate the Executable Catalog

Status: ready-for-dev

## Story

As an evaluator author,
I want one versioned YAML catalog validated structurally and semantically,
So that only atomic, closed, reviewable scenarios can become executable tasks.

## Acceptance Criteria

1. **Given** `evaluation/catalog/catalog.yaml`  
   **When** catalog validation runs  
   **Then** it is the sole hand-authored execution source and is validated with pinned JSON Schema 2020-12 plus semantic and referential-closure rules  
   **And** production code never parses the TEA Markdown scenario table as execution truth.
2. **Given** a scenario  
   **When** it has zero or multiple injected conditions, procedures, or objective verdicts, duplicate or treatment-revealing IDs, or unresolved references  
   **Then** validation fails with source-located typed diagnostics  
   **And** no generated execution artifact is written.
3. **Given** a catalog change relative to its lock  
   **When** the change is breaking, additive, or content-only  
   **Then** validation requires respectively a major, minor, or patch catalog-version increment  
   **And** an insufficient or unrelated version movement fails closed.

## Dependencies and Prerequisites

- **Formal graph dependency:** Story 1.1.
- Story 1.1 must provide the evaluator package, typed domain failures, CLI composition, artifact references, and unpaid fake ports. Every `evaluation/` UPDATE path below is created by that dependency; none exists in the current checkout before Epic 1 implementation starts.
- The QA Markdown table remains a design source only. Migration may be reviewed against it, but runtime/production code must never load it.
- This story validates authored YAML; canonical compilation, fixture verification, eligibility, freezing, assignment, and execution remain future stories.

## Tasks / Subtasks

- [ ] Define catalog schema `1.0.0` and authoritative YAML shape (AC: 1)
  - [ ] Require catalog `schema_version`, semantic `catalog_version`, opaque `catalog_id`, and scenarios.
  - [ ] Require each scenario to carry `id`, `title`, `protocol_ids`, `priority`, `owner`, `preconditions`, `fixture_refs`, `procedure`, `expected_evidence`, `pass_criteria`, `allowed_retries`, `risk_ids`, `gate_ids`, `endpoint_ids`, `claim_ids`, `data_classification`, `network_policy`, `resource_limits`, and `grader_ref`, plus an unambiguous single injected condition.
  - [ ] Forbid YAML anchors, aliases, merge keys, environment substitution, duplicate keys, non-UTF-8 input, NaN, and Infinity.
- [ ] Implement structural validation (AC: 1, 2)
  - [ ] Validate against a locally pinned JSON Schema draft 2020-12 schema.
  - [ ] Convert parser/schema failures to source-located domain diagnostics with stable codes.
  - [ ] Accumulate deterministic diagnostics where safe; write no output on any failure.
- [ ] Implement semantic and referential-closure validation (AC: 1, 2)
  - [ ] Enforce exactly one injected condition, one procedure, and one objective verdict.
  - [ ] Reject duplicate and treatment-revealing IDs.
  - [ ] Resolve protocol, fixture, risk, gate, endpoint, expected-evidence, claim, grader, and other declared references.
- [ ] Implement catalog version policy against the prior valid lock (AC: 3)
  - [ ] Classify breaking, additive, and content-only changes from the validated semantic source projection, not YAML formatting, comments, or parser-specific objects.
  - [ ] Require major, minor, and patch movement respectively and reject unrelated over/under movement.
  - [ ] Keep digest generation out of this story except reading a prior lock contract.
- [ ] Add CLI validation command and unit/contract/golden tests (AC: 1-3)

## Developer Context

The executable source is new `evaluation/catalog/catalog.yaml`; it is not the TEA 161-row Markdown table and is not generated by interpreting prose at runtime. A valid scenario is atomic, reviewable, treatment-neutral, and referentially closed. Validation must complete before any compile write begins.

### Architecture Compliance

- `catalog` may depend on domain-owned types but imports neither Inspect nor Copilot SDK and performs no provider/network calls.
- YAML is human-authored only; execution consumes validated compiled artifacts in Story 1.3.
- Stable IDs are opaque and do not reveal an arm.
- Diagnostics include source path/location, stable code, and human message; failures are typed and non-interactive.
- JSON Schema is draft 2020-12, schema version is `1.0.0`, and version policy is semantic major/minor/patch as stated in the AC.

### Library and Version Requirements

- Python 3.13 and Story 1.1 evaluator lock.
- The final architecture fixes **JSON Schema draft 2020-12**, not a specific Python YAML/schema package. Do not claim an invented package version as architecture. Any selected parser/validator must be declared only in `evaluation/pyproject.toml`, resolved exactly in `evaluation/uv.lock`, support source locations/duplicate-key rejection, and pass contract tests.
- Do not introduce an RFC 8785 implementation here; Story 1.3 owns the single shared canonicalizer.
- `pytest` remains the test runner locked by the evaluator project.

### Expected File Paths

- **NEW:** `evaluation/schemas/scenario.schema.json`
- **UPDATE:** `evaluation/catalog/catalog.yaml`
- **NEW/UPDATE:** `evaluation/src/memrelay_eval/catalog/{loader,validation}.py`
- **UPDATE:** `evaluation/src/memrelay_eval/cli/commands.py`
- **NEW:** `evaluation/tests/unit/catalog/test_loader.py`
- **NEW:** `evaluation/tests/unit/catalog/test_validation.py`
- **NEW:** `evaluation/tests/golden/catalog/`

`catalog.yaml` and CLI modules are dependency-created UPDATE seams. The schema, loader, validator, and tests are new; do not modify the TEA Markdown source or product package to create them.

### Existing Behavior to Preserve

- Story 1.1 domain import purity, typed failures, fake-port eligibility barrier, CLI manifest conventions, and product/evaluator packaging separation.
- Input failures must not modify a prior valid catalog or lock.
- The Markdown design artifacts remain unchanged and non-executable.

### Testing Requirements

- Positive schema and semantic cases plus one failure test for every forbidden condition in AC2.
- Draft assertion proves the pinned schema declares/uses 2020-12.
- Golden diagnostics prove stable ordering, code, path, line/column where available, and no generated writes.
- Referential closure tests cover every reference namespace.
- Required-field tests cover the complete §9.1 scenario shape and prove source paths are repository-relative rather than host-specific absolute paths.
- Version matrix tests cover breaking/additive/content-only, exact required movement, insufficient movement, unrelated movement, and no-change behavior.
- No-network test proves validation cannot call Inspect, Copilot, OpenAI, or any provider.

### Anti-Patterns

- Do not parse TEA Markdown in production or copy its mapping rows by hand.
- Do not silently normalize invalid/composite scenarios into valid ones.
- Do not generate locks/tasks/assignments on a validation failure.
- Do not use sorted-key JSON as a substitute for RFC 8785.
- Do not add live provider discovery, fixtures, eligibility, assignment, or execution.
